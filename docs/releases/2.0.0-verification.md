# FURNACE 2.0.0 verification

Local release checks were completed on 2026-10-17 before publication. The
release candidate was prepared on `develop`; crates.io publication and the
`v2.0.0` GitHub release remain gated by the repository's `main` workflows.

## Workspace and examples

- `cargo +1.99.0 test --locked --workspace --all-features` passed.
- `cargo +1.94.0 test --locked --workspace --all-features` passed.
- Workspace Clippy with all targets and features passed with warnings denied.
- Workspace doctests passed; `cargo doc` passed with rustdoc warnings denied.
- The CLI release-automation suite passed all 25 tests, including the check that
  release documentation follows the latest stable changelog version.
- All stable release feature-boundary checks passed. Package-content policy
  verified the exact payload for all fourteen publishable crates, and Cargo
  packaged all fourteen archives.
- All nine independent examples resolved with locked offline metadata. The
  WebSocket example passed with default and all features; the gRPC example
  passed with gRPC-only and mixed HTTP/gRPC features. The compile-time DI
  example's missing-provider test passed on Rust 1.99 and 1.94. HTTP, CRUD,
  storage, and protected-route examples compiled for all targets. The
  intentionally invalid missing-dependency example failed with its documented
  missing-provider diagnostic.
- Redis-backed room tests passed within both all-features workspace suites,
  including cross-instance live delivery and replay ordering.
- The protected-route example lockfile was missing the socket transport graph.
  Cargo added the required socket entries; existing registry versions and
  checksums stayed unchanged. The example now passes `cargo check --locked`.
- The compile-time DI stable and MSRV snapshots were refreshed after source
  documentation comments shifted the referenced lines in `di_contract.rs`.
  The diagnostic content did not change, and both snapshots pass on their
  matching toolchains.
- Real PostgreSQL 16 validation passed four native connector tests and the
  generated-storage acceptance test.
- The minimum SeaORM 2.0.0 compatibility checks passed for persistence and the
  common response integration.

## Security and release metadata

- `cargo audit` and the lockfile audit passed for all fourteen tracked
  `Cargo.lock` files. Security report integrity passed 21 tests; infrastructure
  and CLI security smoke profiles passed with no failures.
- Version preparation and metadata checks confirmed fourteen publishable
  crates at `2.0.0`, exact local framework pins in manifests and lockfiles,
  unchanged example application versions, and preserved existing external
  dependency versions and checksums.
- Every Unreleased and beta.1, beta.2, and beta.3 changelog entry is represented
  under 2.0.0. The original beta sections remain intact and Unreleased is empty.
- Baseline validation reproduced a timing flaw in the CLI dependency-removal
  regression with a deliberately slow compiler. The fixture now pauses its
  child while updating the manifest and lockfile as one batch, and checks the
  runtime-query marker before its artificial one-second delay. A deliberate
  stale-watch fault triggers the assertion. The other six CLI cargo-execution
  tests pass. The pending-metadata shutdown test times out in this managed
  sandbox because Tokio's signal listener does not observe injected SIGINT; a
  standalone Tokio probe reproduces this behavior. Hosted Linux CI must confirm
  that check. Production watcher and signal handling code were unchanged.

## Repository publication gates

The GitHub pull request and stable publication workflows remain required. They
cover security checks, stable workspace tests, CLI platform tests, Rust 1.94,
SeaORM 2.0.0 compatibility, PostgreSQL, package archives, and the existing 85%
line-coverage threshold. Publication is complete only after the stable workflow
passes and the registry, tag, and GitHub release show version 2.0.0.
