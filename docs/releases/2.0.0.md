# FURNACE 2.0.0

FURNACE 2.0.0 consolidates the entire beta series and the WebSocket transport.
All fourteen publishable workspace crates and local framework dependency pins
use `2.0.0`. Edition 2024 and the Rust **1.94** minimum remain unchanged.
The complete release inventory is in [CHANGELOG.md](../../CHANGELOG.md#200---2026-10-17);
the beta sections remain as historical records.

## Install

```sh
cargo install furnace-rs-cli --version 2.0.0 --locked
```

For a minimal HTTP application:

```toml
[dependencies]
furnace-rs = { version = "=2.0.0", default-features = false, features = ["http", "runtime-tokio"] }
```

To run directly from this checkout, use
`cargo install --path crates/furnace-rs-cli --locked`. Independent examples retain
their own application versions and use exact local framework pins.

## Migration from 1.x

Dependency fields on `#[burner]`, `#[storage]`, and managed `#[controller]`
structs now require parameterless `#[inject]`:

```rust,ignore
#[burner]
struct Service {
    #[inject]
    repository: Repository,
}
```

Every named field on those managed structs is a declared dependency. Unit structs
need no marker. Manual `Injector` implementations continue to declare their
`Dependencies` explicitly. A service layer remains optional.

Declarative `#[cauldron]` lists register providers, controllers, imports,
exports, gRPC services, and socket gateways/endpoints. Mark a selected root with
`root` for dependency availability and visibility checks at compile time.
Legacy fluent roots still work and retain runtime validation. Duplicate output
ownership, cycles, asynchronous construction, configuration and listener binding
still require runtime validation; compile-time DI does not replace them.
See the [DI guide](../declarative-di.md) and
[compile-time example](../../example/compile-time-di/).

## Transports and delivery

HTTP remains available through the normal facade defaults. Optional transports
use the same root, application providers, readiness and shutdown lifecycle:

| Integration | Packages and facade features |
| --- | --- |
| gRPC | `furnace-rs-grpc`, `furnace-rs-grpc-macros`; `grpc`, `grpc-tls`, shared `jwt` |
| WebSocket | `furnace-rs-socket`, `furnace-rs-socket-macros`; `socket`, `socket-tls`, `socket-redis`, shared `jwt` |
| Entity storage | `furnace-rs-persistence`, `furnace-rs-persistence-types`; optional `sea-orm-storage` and PostgreSQL support |

Select transports explicitly with `[furnace] transports` when using gRPC or
WebSockets. They use separate configured listeners and participate in shared
startup, rollback and bounded drain. Native TLS and proxy termination are
supported. Supplied browser origins require an explicit WebSocket allowlist.

The [gRPC guide](../grpc.md) covers all four native RPC shapes, generated
application-owned protobuf types, named injectable clients, method admission,
health and scoped reflection. The [WebSocket guide](../socket.md) covers raw and
named JSON gateways, owned sockets, handshake admission, dynamic authorized
rooms, bounds and heartbeats, and local or distributed delivery.

Replayable rooms require Redis **6.2+** and explicit age and count retention.
Client-held room cursors allow ordered catch-up and live continuation. There is
no client acknowledgement tracking or exactly-once guarantee. During a Redis
outage, distributed sends fail explicitly while existing connections and local
direct sends remain available. Room deletion requires empty leased membership.

## Entity storage

`#[storage(entity = ...)]` provides optional native SeaORM CRUD, typed filters,
explicit ascending/descending ordering, relation loading and one-based page
pagination. Pagination loads the requested parent page without a total count or
lookahead; applications own limits and transactions. The HTTP integration can
convert storage failures with `?` into redacted 500 responses while preserving
explicit handler mappings. See the [storage guide](../storage.md) and
[storage example](../../example/posts-crud-storage/).

## CLI, security and lifecycle corrections

`furnace grpc` and `furnace socket` join HTTP/graph/doctor inspection. Inspection
reads selected static metadata without constructing providers, binding listeners,
reading TLS identities or contacting Redis. The CLI preserves invocation Cargo
configuration and runtime library paths and reloads declared build inputs and
dependency graph changes during development.

The stable release includes conditional gRPC admission fixes, resumable lifecycle
cleanup, configuration merge/validation corrections, safe cookie names and
attributes, body-timeout response header preservation, accepted socket peer
metadata, redacted extractor errors, native database timeout validation and
inventory output type checks. Historical security evidence remains attached to
its original source hashes and commits; it is not a claim of exhaustive review
of every new transport. Applications still own authorization decisions,
credentials, keys, revocation, migrations and deployment resource policy.
See the [security policy](../SECURITY.md), [audit index](../SECURITY_AUDIT.md),
and [benchmark security evidence](../../benchmark/SECURITY.md).

## Release verification and publication

The release process validates workspace tests, documentation, feature boundaries,
Rust 1.94, real Redis and PostgreSQL acceptance, dependency advisories, CLI/core
security contracts, package payloads and exact internal version/lockfile alignment.
Preparation results are recorded in [the verification record](2.0.0-verification.md).

Publication uses `.github/workflows/stable-publish.yml` after integration into
`main`. Its required jobs additionally cover CLI platform behavior,
SeaORM 2.0.0 compatibility and the existing 85% line-coverage threshold. General
CI also verifies JWT algorithms, rotation and platform behavior. The
workflow publishes all fourteen crates in dependency order, then creates
`v2.0.0` and the GitHub release. Registry/Git dependency records retain their
original published versions and checksums during local version preparation.
